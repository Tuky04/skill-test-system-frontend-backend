# คู่มือย้ายจากระบบเดิม

อย่ารัน migration กับฐานจริงโดยไม่มี backup และ staging rehearsal

## ลำดับ

1. ปิดการเขียนข้อมูลชั่วคราวและสำรอง DB กับโฟลเดอร์ `backend/uploads`
2. รัน `backend/migrations/001_preflight.sql`
3. แก้ข้อมูลซ้ำ/foreign key กำพร้าทุกรายการ และตรวจคะแนน `0/0/0` ด้วยหลักฐานการเข้าสอบ
4. ทดสอบ `backend/migrations/002_hardening.sql` และ `003_university_student_code.sql` บนสำเนา staging
5. เมื่อผลถูกต้องจึงรัน migration ตามลำดับกับ production
6. คัดลอกไฟล์จาก `backend/uploads` ไป `backend/private_uploads` โดยคงชื่อเดิม แล้วตรวจจำนวน/ขนาด/hash ก่อนสลับระบบ
7. ห้ามเปิด static route `/uploads`; เอกสารต้องเปิดผ่าน `/api/documents/:filename` เท่านั้น
8. deploy backend/frontend ชุดใหม่และทดสอบ smoke test

## กติกาข้อมูลเดิม

- บัญชีเดิมถูกกำหนดว่าอีเมลยืนยันแล้ว เพื่อไม่ล็อกผู้ใช้ทั้งหมดทันที
- ผลคะแนนที่มีค่าอย่างน้อยหนึ่งช่องไม่เป็นศูนย์จะถูกถือว่าเคยประกาศผล และตั้งสถานะ `ประกาศผลแล้ว`
- คะแนน `0/0/0` ไม่ถูกประกาศอัตโนมัติ เพราะอาจเป็นคะแนนจริงหรือข้อมูล placeholder เดิม ต้องพิจารณาทีละรายการ
- consent ของผู้ใช้เดิมเป็น `NULL`; ควรทำหน้าขอความยินยอม/รับทราบประกาศใหม่ก่อนกิจกรรมถัดไป ห้ามใส่วันย้อนหลังแทนผู้ใช้
- `university_student_code` ของผู้สมัครเดิมจะเป็น `NULL`; ผู้ดูแลต้องเติมรหัสจริงและตรวจไม่ให้ซ้ำ
- migration เพิ่มประวัติเอกสารปัจจุบันเป็นเวอร์ชันแรก ส่วนไฟล์เวอร์ชันเก่าที่ไม่มี metadata จะกู้ประวัติไม่ได้

## ตรวจหลังย้าย

- จำนวน users/students/registrations/scores ก่อนและหลังตรงกัน
- email และ application number ไม่ซ้ำ
- เอกสารตัวอย่างแต่ละ role เปิดได้/ถูกปฏิเสธถูกต้อง
- นักศึกษาที่ยังไม่ประกาศผลไม่เห็นว่าไม่ผ่านและสมัครซ่อมไม่ได้
- รายงานผู้สมัคร/ผ่าน/ไม่ผ่าน/รอคะแนนตรงกับ SQL ตรวจสอบอิสระ
